## Context

两项改动都不触碰代码:年历是纯数据文件,`calendar.py` 的匹配逻辑对 `{date, bank, event}` 是通用的;trigger 约束是 prompt 措辞。

## Goals / Non-Goals

- Goals:让"下个催化剂是哪天"有确定性答案;让复盘能产出命中/未命中而非恒为无法判定
- Non-Goals:不改采集层与校验器;不为无法验证的日程编造日期

## Decisions

1. **`bank` 字段复用为"发布方"**。schema 不变(calendar.py 要求 `bank`/`event` 均为 str),数据发布条目的 `bank` 填 `BLS`/`Fed`。相比新增 `issuer` 字段,复用避免改代码;字段名与语义的偏差写进 `maintenance` 说明。
2. **只录可验证条目**。BLS CPI 与 Employment Situation 的 2026 全年日程、美联储已公布的 FOMC 纪要日期均从官网取得并记录 URL 与抓取日期;PH/TH/BR/EA 的统计发布日历(PSA、IBGE 等)官网对本机返回 HTTP 403,**不录入任何推测日期**——年历的价值全在可信,宁缺毋编。缺口写进 `maintenance`。
3. **未公布的 FOMC 纪要日期不按规则外推**。美联储页面写明"纪要在政策决定后三周发布",据此可算出 7 月会议纪要约在 8 月 19 日,但该页面对这几场标注"not yet posted"。规则外推值与官方公布值可能差一天,而年历的用途是给报告写"具体哪天",错一天即误导——不录。
4. **trigger 约束写在决策日志与复盘两处**。只改模板不解释原因,长上下文里容易退化;两处都写明"绑系统自身状态的触发条件不可证伪",让约束自带理由。

## Risks / Trade-offs

- [数据发布条目让 `calendar_hits` 变密,可能挤占报告篇幅] → 命中项本就只在"年历命中"行逐条列出,且日报有 300 字/节上限兜底
- [年历只覆盖美国,其余四经济体仍无发布日程] → 如实写进 `maintenance`;美国 CPI/非农本就是五币种共同的最大催化剂,覆盖它已解决大部分场景
- [trigger 约束可能让某些日子写不出触发条件] → 允许"若年历上的 X 日事件落地并显示 Y"这类形态,采集失败日仍可绑存量指标(上一 change 的存量背景回退提供了数值锚点)

## Migration Plan

纯数据与 prompt 改动,历史报告不回填。回滚 = git revert。
